# M4 Implementation Plan — Election, Failover, and Rejoin

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Elect a new primary within five seconds, preserve committed operations, reconnect clients through `PRIM`, and automatically rejoin the old primary via snapshot.

**Architecture:** All nodes run a `ClusterNode` with periodic heartbeats, persistent terms, and majority election. All nodes listen for mTLS replication control messages. The leader sends `SNAP` to lagging peers. Clients use `CLIENT_PEERS` as seeds, ask `PRIM` for the current primary client endpoint, reconnect, and reconcile before retrying the outbox.

**Tech Stack:** Python 3.10+, `unittest`, TLS/mTLS, SQLite, sockets, `trustme`, Docker Compose.

## Decisions

1. Election requires a majority (2/3), candidate `(last_term, last_index)` at least as high as the voter's, random election jitter, and lowest `server_id` as final tie-break.
2. Terms and votes are persisted. A higher term forces follower and clears the vote.
3. Leader steps down if it cannot obtain majority `HB_OK` within `FAILURE_TIMEOUT`.
4. Rejoin is automatic: leader detects lagging `commit_index` and sends `SNAP`.
5. Client discovery uses `PRIM`; `CLIENT_PEERS` provides seeds and fallback.
6. Client reconnects, reconciles, then replays the remaining outbox.
7. A configured primary starts as leader only on first boot (`initialized` absent); after restart it starts as follower.
8. Standalone mode has no election and stays leader.
