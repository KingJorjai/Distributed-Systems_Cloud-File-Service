Implementing our cloud service¶

The Project of the course consists of the final implementation of the cloud file service tolerant to failures from the ideas and concepts introduced during the course. Part of the project is developed and evaluated within some of the activities, specifically in Part 1 and Part 3, so here we are referring to the integration of the modules previously developed, to complete the functionality of the service, to the preparation of the documentation and the oral presentation of the project. For these aspects a dedication of 20 hours by each member of the group is estimated.

It should be borne in mind that with the estimated dedication it is not possible to finish the implementation until obtaining a complete service in the style of those that exist commercially. What we want is a proof of concept to demonstrate that, with the necessary time, we would be able to build a complete cloud service. The evaluation of the work goes in this line: the important thing is to correctly implement a defined part making clear what has been done and what remains to be done.

It is important to follow a modular and incremental structure, as described below.

Incremental development¶

We can distinguish three phases in the development.

  1. Unreliable Client-Server. A single client sends requests transparently to a non-replicated server. This is the work proposed in Part 1.

  2. Fault tolerant server. The server is replicated according to the passive replication technique. Communication support (broadcast primitives) must be implemented, and fault situations identified. In a separate module, an algorithm to detect a primary fault must be implemented, as well as a distributed algorithm of election of a new primary. These modules are designed on some of the activities in Part 3.

  3. Client-Server sharing files. Several clients send requests on a shared file. The server notifies clients of the modification so that they update their local copies.

Try to simplify to the maximum, since it is a proof of concept. For this, some measures are suggested:

  • Mount the system on a single machine, associating names of clients and servers with ports.

  • Although it is valued that the solution is as general as possible, restrict the tests to only three servers (primary and two secondary) and two clients.

  • You can delegate some functions to do them by manual configuration (for example, to deal with some failure situation, to update the state in case of change of primary, etc).

It is important that you follow the incremental design and make intelligent decisions to optimize your time. Organize group work by distributing roles and tasks, but do not disregard the work of colleagues. For example, if one develops, have another verify that code.

Presentation of the results¶

It is necessary to present a written report and the code developed. We will also dedicate a class to the oral presentation of the results. For planning reasons, the oral presentation must be done before the final version of the report is delivered. For the date of the oral presentation it will be necessary to have a draft of the report, which will be used to identify the issues to be improved for the final version.

Once the memory is delivered, you will be asked for a demonstration of the operation of the service.

Final report¶

The report of the project will have the following structure:

  1. A description of the problem to be solved and the specific implementation objectives.

  2. A description of the approach followed, the modular architecture and the concrete solutions applied to each part.

  3. A reasoned explanation of the implementation decisions taken, with references to the code developed.

  4. A reasoned explanation of the tests performed and the results obtained.

  5. The conclusions and final considerations. In particular, it is important to describe what remains to be developed.

Oral presentation¶

We will dedicate a maximum of 15 minutes to the presentation of the partial results of the project for each group, with 5 additional minutes for questions. Each group member will present a part:

  1. The approach, architecture and design decisions.

  2. Description of the parts implemented, what remains pending, and what is not going to be implemented.

  3. Tests performed, with the conclusions obtained, and tests pending.

Evaluation¶

The project is evaluated as 20% of the total grade based on the report delivered, the code developed and the oral presentation in class. The specific evaluation criteria are as follows:

Report¶

All members of the group are evaluated equally according to the following criteria:

  • Structure. It is well valued if it complies with what is specified, the different sections are linked so that they help the reader to locate himself, contain an index, some conclusions and references to the bibliography and/or resources used.

  • Content. It is well valued if it is original and does not include copied content, the ideas are well synthesized and the reasoning is consistent, uses precise terms demonstrating that the concepts have been understood, includes useful illustrations to complement the descriptions and describes the parts of the project that are not finished.

  • Legibility. It is well valued if the text is pleasant to read, grammatical structures are well constructed and does not contain misspellings.

  • Presentation. It is well valued if the format is homogeneous and the presentation is attractive to the reader.

Code¶

All members of the group are evaluated equally according to the following criteria:

  • Correction. It is well valued if it meets the established functional requirements, the tests performed are consistent with the specification and the verification collects the test results faithfully.

  • Modularity. It is well valued if it respects the proposed modularity.

  • Clarity. It is well valued if it is structured and easily followed.

  • Efficiency. It is well valued if it is not evident that it can be specified more compactly or that the solution can be programmed so that it uses fewer computing and communication resources.

Oral presentation¶

It is evaluated according to the following criteria:

  • Content. It is well valued if the main ideas are synthesized, listeners are not overwhelmed with superfluous details, precise terms are used with clear language and the questions asked are satisfactorily answered.

  • Formal aspects. It is well valued if the material used for the presentation is well structured, the presentation is well coordinated and is homogeneous among the members of the group, the speaker shows a respectful attitude towards the audience, efficiently uses the presentation resources and time is not exceeded.

It is important to keep in mind that it is not intended to evaluate the particular ability to speak in public, but the attitude shown to learn to do so.
