1. INTRODUCTION

In a distributed file service, clients and servers have independent clocks.
Message transmission takes time, so the timestamp of a modification cannot be
treated as an exact global ordering. This matters when two users modify a
shared document: if the clock error is comparable with the time between
modifications, the service must report an uncertain or concurrent update
instead of silently choosing an order.

This report defines the requirements for useful time, proposes synchronization
without an external reference, summarizes NTP, and analyzes the class
simulation using NTP symmetric operation and Cristian's algorithm. The
terminology and algorithmic background follow Sections 2.2 and 2.2.1 of the
Topic 2 notes.


2. WHAT IS GOOD TIME?

Time is good only with respect to a reference and an application. External
synchronization compares a local clock with a reliable physical reference such
as UTC. Internal synchronization instead bounds the difference between the
clocks of the nodes in one distributed system; this is usually the relevant
goal for ordering file-service events.

Important quantities are:

* Deviation (offset), theta: the difference between a local clock and the
  reference at an instant.
* Precision/accuracy: the maximum error that can be guaranteed after an
  adjustment.
* Drift: the rate at which the deviation changes.
* Resolution: the smallest interval represented by the clock.

A clock may have fine resolution but poor accuracy, or be accurate immediately
after synchronization and become inaccurate because of drift. Network delay,
congestion, operating-system scheduling, oscillator quality and temperature
also affect the result. Therefore, the report must state both an estimated
deviation and its uncertainty.

The notes define a synchronization period as the maximum interval between two
adjustments that keeps the deviation within the required bound. The adjustment
period is the time used to accelerate or decelerate the software clock to
compensate for the deviation, and must be shorter than the synchronization
period. Gradual correction is preferable to a backward jump because it
preserves the monotonic increase of time, which applications may rely on.


3. SYNCHRONIZATION WITHOUT AN EXTERNAL REFERENCE

Let A and B exchange messages without trusting timestamps added by the
communication service. A can be the reference for one round:

1. A records T1 and sends a request.
2. B records T2 on receipt and T3 immediately before replying.
3. A records T4 on receipt of the reply.
4. A estimates B's deviation and sends a correction.

Let t and t' be the forward and reverse communication times, and let theta be
B minus A. Then:

    T2 = T1 + t + theta
    T4 = T3 + t' - theta

The four timestamps give:

    d = (T2 - T1) + (T4 - T3) = t + t'
    theta = (T2 - T1 + T3 - T4) / 2

Without knowing t and t' separately, the conservative error bound is d/2.
Thus, the estimate is useful only together with its accuracy interval. Several
rounds should be made and the smallest-delay sample selected, since it gives
the narrowest possible interval. Synchronization must be repeated to account
for clock drift.

For several nodes, a coordinator can collect estimates, reject missing or
clearly spurious responses, calculate an internal reference (for example, an
average or median), and distribute each node's correction. This is an internal
reference, not UTC. A distributed statistical approach such as Berkeley's
algorithm avoids depending permanently on one time server and can select a new
coordinator after a failure.


4. NTP INFRASTRUCTURE AND OPERATION

The Network Time Protocol (NTP) provides redundant synchronization with UTC.
Its hierarchy is organized into strata: primary servers obtain a reference
from reliable clocks, secondary servers synchronize with them, and lower
layers serve clients. Accuracy generally decreases as the number of network
hops from the UTC source increases, so several sources are used and the
logical structure can be reconfigured when a server becomes unavailable.

NTP supports multiple modes. Multicast is suitable for a local network with
bounded communication time. Procedure-call mode resembles Cristian's
client/server exchange. Symmetric mode is intended for strong internal
synchronization: two servers exchange timing information and both adjust
their clocks. NTP uses an algorithm similar to Cristian's to estimate
deviation and precision, but its symmetric mode uses a double exchange to
compensate communication delays.

In Linux, the active implementation depends on the distribution. Useful
inspection commands are:

    timedatectl status
    timedatectl show-timesync --all
    chronyc sources -v
    chronyc tracking

A practical configuration should use several trusted servers, start the time
service automatically, and restrict unsolicited access when the host serves
time. The service should discipline the software clock gradually whenever
possible.


5. NTP SYMMETRIC PROTOCOL: CLASS SIMULATION

The experiment used A as the client/reference clock and B as the peer. The
measured results were:

    Deviation (B - A)             +38.00 s
    Communication time (t + t')   40.00 s
    Accuracy                       +/-20.00 s

The 40 seconds are the communication time represented by t+t' in the NTP
calculation. They are not the complete request-response interval. The
experiment introduced a 40-second difference between the server readings T2
and T3, which is consistent with this communication-time result.

Using the NTP convention server minus client:

    theta_NTP = (T2 - T1 + T3 - T4) / 2 = +38.00 s

B is therefore estimated to be 38 seconds ahead of A. Synchronizing B to A
would require a correction of -38 seconds, applied according to the selected
clock-discipline policy. Since only t+t' is bounded, the accuracy is:

    accuracy = (t + t') / 2 = 40.00 / 2 = +/-20.00 s

The result should consequently be reported as +38.00 s +/-20.00 s, not as an
exact 38-second difference. Repeating the exchange and choosing low-delay
measurements can reduce the uncertainty, but variable and asymmetric delays
cannot be eliminated entirely.


6. COMPARISON WITH CRISTIAN'S ALGORITHM

In the same exercise, Cristian's client A measured a complete request-response
interval of:

    D = 122.00 s

Cristian estimates the server time at the midpoint of the client interval.
Using the midpoint between the server readings T2 and T3, the deviation with
the convention client minus server is:

    theta_Cristian = A - B = -38.00 s

Thus, A is 38 seconds behind B. This is the same physical relationship as
the NTP result; the signs differ because NTP reports B-A whereas Cristian is
reported as A-B.

From the Topic 2 notes, Cristian's accuracy is:

    accuracy = D / 2 - min

No positive minimum transmission time was available in this experiment, so
min = 0 and:

    accuracy = 122.00 / 2 = +/-61.00 s

The Cristian result is therefore -38.00 s +/-61.00 s. NTP gives the narrower
bound in this experiment (20 seconds versus 61 seconds) because the NTP
calculation uses the communication-time estimate from the four timestamps,
while Cristian uses the complete request-response interval.

Cristian's main advantages are simplicity and its small number of messages. It
is appropriate when a client trusts a server and only needs approximate time.
Its disadvantages are dependence on that server, sensitivity to the measured
request-response delay, and lower fault tolerance. Replicating the server
improves availability but introduces another synchronization problem.

NTP is more complex, but supports several sources, strata, filtering,
reconfiguration, drift compensation and symmetric peer synchronization. Its
accuracy remains limited by network delay and it requires more configuration.
Neither method proves that two close file modifications are causally ordered:
when their separation is below the uncertainty bound, the file service should
use versions, causal metadata or explicit conflict detection.


7. CONCLUSIONS

Useful time is time whose deviation, drift and resolution are bounded relative
to the application's reference. For a cloud file service, internal
synchronization is often more important than exact UTC: all nodes need
comparable timestamps and a known uncertainty.

The class NTP simulation estimated B's clock as +38.00 seconds relative to A,
with accuracy +/-20.00 seconds. Cristian's calculation described the same
relationship as -38.00 seconds (A relative to B), with accuracy +/-61.00
seconds. The comparison illustrates why the sign convention and the accuracy
must always be stated.

Clock synchronization improves event ordering but cannot remove concurrent
updates or network uncertainty. Consequently, timestamps should support, not
replace, versioning and conflict-resolution mechanisms in the shared file
service.
